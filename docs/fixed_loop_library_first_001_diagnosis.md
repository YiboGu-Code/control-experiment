## 根因与修改

### 合法地砖和开关被当作人物

`terrain_stone_block.png` 和 `laserSwitchBlueOff.png` 都声明为 `sprite`，被矩形、底座和边界接触检查拒收。协议原本缺少单块地形、世界道具类型，`tile_set` 又要求真正拆图集。

新增 `layout.kind=tile/prop`，共享 `asset-pixels.v4` 按用途检查：人物维持完整背景/地台检查，地形允许实心矩形，道具允许自己的底座和方形主体。空图、异常处理报告、生成图的透明度失败仍拒收；道具仍检查疑似文字碎片。已拒绝的人物不能在修复轮改名为道具/地砖逃过检查。

真实地砖和原世界开关的离线验证显示：人物分类会拒绝，正确分类能产生可用帧，尺寸与 RGBA 像素完全一致。图片、许可证、SHA 固定在测试夹具中。结构通过仍不代表对象身份、视角或视觉质量通过。

### 透明背景质量失败被当作接口故障

`image_calls/008` 的 DashScope 请求为 HTTP 200，返回可解码的 HUD 按钮图片；实际问题是没有可用透明区域。旧处理器抛异常，使整个 Art 调用回滚，有限质量修复根本收不到反馈。

显式布局任务现在保存原生 PNG，将问题记录为 `missing_transparency/empty_sprite`，经共享规范化隔离为零可用帧，再进入现有有限修复。已合格素材不重新生成。无布局旧接口继续失败关闭；鉴权、网络、损坏数据、权限、预算异常仍是真实错误。已用原失败图重现，并通过公共执行器验证只重做失败项。

### 库搜索过宽且没有逐项范围

第二轮每个库都用 player/ghost/tile/ui/font/switch/door 等大串词查询，结果第一页只有门和开关，却被用于决定多种素材走生成。第三轮 `switch button ...` 又找到了 Nintendo Switch 输入图标。

正式规范化模式下，生图回退引用的搜索必须包含本素材的 `asset_ids`。每个查询最多四个相关变体，每轮最多十二条独立查询，仍逐条计工具调用、遵守原有三轮搜索和总预算。提示词要求按主体检索、细化或翻页，明确世界开关不是手柄按键、侧视门不是等距建筑。宿主还会拒绝把路径明确属于 input-prompts/input-icons/controller-prompts 的输入图标当作人物、地形或世界道具；作为 UI 提示仍合法。范围和类别校验不声称自动证明其他素材的语义匹配，仍需预览和 QA。

### 打包选择了菜单操作，遗漏后来的进关轨迹

原 `demo_01` 是 120 帧菜单操作，同轮 Player 后来录到了 420 帧的进关操作。旧规则拿第一个普通入口，没考虑实际输入丰富程度。

现在普通入口和命名场景各保留一个；同类优先新探索，再按输入种类、有效动作数、时长排序。真实记录验证选择变为 `ordinary_title_level1_play_probe-capture`。这只是候选排序，不是自动判定玩法成功；保留原始字节、来源、SHA，新版本仍必须重放，模型不能编造交付轨迹。

### 已修缺陷被未测需求拖住

QA 已确认倒计时、HUD 遮挡和屏幕边界修复，但关联需求里还有跳跃/重置未测，旧宿主要求整条需求通过，导致原 Developer 问题继续保留。

具体 runtime/gameplay/trace/visual 缺陷可通过 `resolved_criteria` 指明证明修复的当前通过项，必须提供前次评审之后的新证据、对应来源和修复说明。视觉关闭仍需实际提供的像素。其余未通过项保留独立问题，整条需求和交付 gate 不放宽。design/evidence_gap 仍使用完整关联需求通过的规则。

### 实测结果无法补关联

Player 原先只能在运行前绑定需求，实际看到的额外内容无法供 QA 使用。新增 `evidence_mappings`，引用本次成功 capture 的实际检查点并说明关联；拒绝 probe、replay、未来会话、未保存帧、未知需求。只补相关性，不改变输入、像素、重放或验收结论。

Player 提示词要求优先覆盖待办，并在短暂反馈前中后设置检查点；Designer 不得把“精致”扩写成额外建筑约束；Developer 需要检查道具身份、碰撞/交互范围和出口遮挡。
