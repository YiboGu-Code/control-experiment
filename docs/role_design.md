## 1. 项目目标与系统边界

本项目比较固定 Loop 与 Scheduler 调度两种范式在 GameCraft-Bench 游戏生成任务上的效果。核心问题是：在角色能力、工具、输入信息和资源预算相同的条件下，自适应选择下一步工作是否能够提高最终游戏质量或资源利用效率。

系统采用 **5 个工作角色 + 1 个可替换控制器**：

- Designer：需求与玩法设计者。
- Art Producer：美术与界面资源制作者。
- Developer：游戏开发与集成者。
- Player：试玩与证据采集者。
- QA Reviewer：需求验收与质量审查者。
- Controller：固定 Loop 或自适应 Scheduler。

角色表示可调用的能力与职责，不要求每个角色常驻一个独立进程。第一版采用串行调用，共享同一套项目状态。

### 1.1 黑盒输入与输出

```text
任务输入：GameCraft-Bench 的游戏 instruction
运行条件：固定的引擎、初始工作区、素材库、工具与资源预算
                         ↓
            控制器 + 五个工作角色 + 共享状态
                         ↓
交付输出：可运行、可游玩的 Godot 项目 + 可重放的 demo 操作轨迹
                         ↓
              外部 GameCraft-Bench 评测
```

instruction 是任务语义输入；引擎、资源、工具和预算是两组实验共用的运行条件。生成过程不依赖人工补充设计或人工修复。

GameCraft-Bench 的交付不能只包含源代码或截图。根据项目内的任务说明，还需要完整游戏项目以及 `demo_outputs/` 中的操作轨迹，由外部评测器启动游戏并重放。交付的游戏项目应能在约定的 Godot 环境中运行，不默认要求额外导出独立安装包。

隐藏 rubric、参考解答及正式评分结果不进入生成黑盒。即使这些文件存在于宿主项目中，运行时也应通过工作区与工具访问范围隔离，不能仅依赖角色提示词。

### 1.2 三层结构

| 层次 | 组成 | 职责 |
| --- | --- | --- |
| 控制层 | FixedLoopController / AdaptiveScheduler | 决定下一步调用哪个角色、处理哪个事项；执行统一的停止与预算规则 |
| 工作层 | 五个工作角色 | 设计、制作、实现、试玩和验收 |
| 执行与存储层 | 工具执行器、项目工作区、状态存储、日志与预算记录 | 执行文件与引擎操作，保存产物，落实权限和调用限制 |

执行与存储层不额外充当智能角色。正式 Benchmark Judge 位于系统外部。

## 2. 角色定义

### 2.1 Designer：需求与玩法设计者

**目标：把原始 instruction 转换成可实现、可验证且可追溯的游戏规格。**

输入：原始 instruction、允许的环境与资源信息、已有设计、相关问题单。

职责：

- 提取明确要求，为需求分配稳定编号，并保留对应的 instruction 依据。
- 定义核心玩法、操作方式、状态转换、胜负条件、重试及返回流程。
- 设计关卡、数值、叙事分支、进度等任务所需内容。
- 说明视觉反馈、UI 状态和素材需求。
- 给出可观察的验收条件，以及需求之间的依赖关系。
- 根据反馈修订实现方案，并记录变更原因。

输出：需求清单、游戏设计规格、内容配置方案、素材需求和验收条件。

边界：

- 不直接调用其他角色，也不决定全局执行顺序。
- 不为降低实现难度而删除 instruction 明确要求的功能、内容数量或表现要求。
- 对未明确的细节作合理假设，并把假设与明确要求分开记录。
- 后续调用可仅修订相关部分，无需每轮重写全部设计。

### 2.2 Art Producer：美术与界面资源制作者

**目标：提供符合游戏需求、视觉一致且能够接入引擎的资源与样式规范。**

输入：设计规格、素材需求、允许使用的素材库、当前视觉证据和相关问题单。

职责：

- 检索并选择适合的现有素材；在实验工具配置允许时制作或生成素材。
- 确定配色、字体、角色与场景风格、UI 样式及状态反馈资源。
- 准备贴图、图集、动画帧、图标等所需资源。
- 记录素材来源与许可，以及尺寸、缩放、动画帧和接入方式。
- 根据实际游戏截图修正资源或样式问题。

输出：素材文件、素材清单、视觉规范及接入说明。

边界：

- 第一版不直接修改游戏逻辑或 Godot 场景，由 Developer 统一接入。
- 修改已被使用的素材时，标记受影响的界面或场景，供后续集成和验证。
- 两组实验使用相同的素材访问范围及生成工具配置，相关调用计入资源消耗。

### 2.3 Developer：游戏开发与集成者

**目标：交付完整可运行的游戏，并持续修复实现缺陷。**

输入：原始 instruction、设计规格、素材及接入说明、当前项目、分配的问题单。

职责：

- 实现游戏规则、场景、交互、UI 行为、内容和进度系统。
- 接入美术资源，维护项目配置、资源引用和启动入口。
- 依据试玩证据与问题单定位并修复缺陷。
- 实现任务协议需要的确定性场景入口与随机种子控制。
- 执行基础导入、解析、启动及相关实现自检。
- 提交变更记录，标明受影响的需求及需要重新验证的部分。

输出：Godot 项目变更、集成结果、基础检查日志和影响范围。

边界：

- 第一版由 Developer 统一维护游戏脚本、场景和项目配置。
- 可以做有界的内部检查与修复，但调用预算和重试规则对两组一致。
- 不能凭实现声明将需求标记为验收通过。
- 确定性 demo 场景应复用实际游戏规则；普通游戏入口仍需支持正常游玩流程。

### 2.4 Player：试玩与证据采集者

**目标：通过真实运行与操作获得游戏行为证据，并产出可重放的演示轨迹。**

输入：当前游戏版本、操作说明、待验证需求、已有轨迹及复现请求。

职责：

- 启动游戏，实际执行菜单、核心玩法、状态变化和结果流程。
- 探索或复现问题，记录操作步骤、观察结果及运行日志。
- 生成符合任务协议的鼠标与键盘输入轨迹。
- 重放轨迹，确认其在对应版本和新启动环境下仍可执行。
- 收集截图或录像，并标注它们覆盖的需求与游戏版本。
- 区分游戏缺陷、轨迹失效、工具错误与尚未探索到的状态。

输出：demo 输入轨迹、截图或录像、日志、操作记录、观察报告。

边界：

- 不修改游戏代码、场景或规则；可写入自己的轨迹与证据产物。
- 需要新的可测试场景时提出请求，由 Developer 实现。
- 报告观察事实及不确定性，不把没有观察到的功能直接判定为不存在。
- 普通入口流程和指定场景都应按需求验证，不能只检查预设的结果画面。
- 轨迹数量、时长、分辨率和事件格式以所固定 Benchmark 版本的任务协议为准。

### 2.5 QA Reviewer：需求验收与质量审查者

**目标：根据原始需求和实际证据判断完成度，形成可执行的问题清单。**

输入：原始 instruction、需求与设计规格、当前产物、试玩证据、历史问题单。

职责：

- 核对设计与实现是否遗漏或偏离原始需求。
- 审查玩法、内容、功能性视觉反馈和美术表现是否符合要求。
- 将证据映射到具体需求，区分已实现、已验证和证据不足。
- 生成问题单，记录类型、严重程度、复现步骤、证据和建议处理角色。
- 根据重新验证的证据关闭或保留问题。
- 给出内部交付就绪判断，交由控制器应用共同的停止规则。

输出：需求覆盖表、问题清单、验证结论、内部交付就绪判断。

边界：

- 不直接修复游戏，也不直接调用其他角色。
- 不读取隐藏 rubric，不调用正式评测获取反馈，不冒充外部 Benchmark Judge。
- 原始 instruction 始终是验收依据，Designer 的规格不是唯一依据。
- 可结合源代码辅助定位问题，但涉及运行表现的验收必须有相应运行证据。
- 内部覆盖率与就绪判断不能替代最终官方分数。

## 3. 关键协作边界

| 边界 | 约定 |
| --- | --- |
| Designer 与 Controller | Designer 描述需求和依赖；Controller 安排角色调用 |
| Art Producer 与 Developer | Art Producer 提供资源和样式规范；Developer 负责引擎接入与最终集成 |
| Developer 与 QA | Developer 实现并自检；QA 根据需求和证据进行验收 |
| Player 与 QA | Player 采集事实；QA 判断事实是否满足需求，并形成问题单 |
| QA 与外部 Judge | QA 是生成过程的内部反馈角色；外部 Judge 仅用于正式评测 |

例如，“升级效果没有生效”的处理过程应为：

1. Player 实际操作升级，记录金币变化和攻击表现，提供轨迹与观察结果。
2. QA 对照需求建立问题单，必要时要求更多证据。
3. Controller 安排 Developer 修复相关实现。
4. Player 在新版本重新执行相关操作。
5. QA 根据新证据关闭或保留问题。

角色之间通过共享状态与产物协作，不自行递归调用其他角色，以便控制器记录完整调用顺序和资源消耗。

## 4. 共享状态与产物契约

两种控制器共用同一份状态结构、读取规则和上下文构造逻辑。角色不应仅依赖一段不断增长的聊天历史。

| 状态项 | 建议内容 |
| --- | --- |
| TaskSpec | 原始 instruction、任务标识、环境约束；原始输入保持不变 |
| Requirements | 需求编号、原文依据、验收条件、依赖、实现与验证状态 |
| DesignSpec | 玩法、状态机、内容结构、操作与视觉约定、修订记录 |
| AssetManifest | 素材路径、用途、规格、来源、许可、版本 |
| GameRevision | 当前游戏版本、变更摘要、受影响需求、基础运行状态 |
| IssueTracker | 问题编号、关联需求、类型、严重程度、证据、建议处理角色、状态 |
| EvidenceStore | 轨迹、截图、录像、日志、观察报告及其对应的游戏版本 |
| RunLedger | 调用序列、角色与控制器消耗、工具耗时、剩余预算、终止原因 |

建议需求验证状态至少包含：`not_implemented`、`implemented_unverified`、`verified_pass`、`verified_fail`。新版本产生后，受影响的旧验证结果应回到待验证状态；原始证据保留用于追溯，不能直接用于证明新版本通过。

每次角色调用使用统一结构：

```text
RoleRequest
  role              要调用的角色
  work_item_ids     关联需求或问题编号
  objective         本次工作目标
  completion_criteria 本次工作完成条件
  state_revision    输入状态版本
  artifact_refs     需要读取的产物引用
  limits            框架注入的统一单次调用限制

RoleResult
  status            completed / partial / blocked / no_op / failed
  summary           完成情况与未解决事项
  artifact_refs     新增或更新的产物引用
  proposed_updates  对需求、问题和验证状态的更新建议
  evidence_refs     本次结论对应的证据
  blockers          尚缺少的依赖或执行条件
```

执行框架负责校验角色是否有权更新对应产物或状态，并记录实际资源消耗。角色声明完成，不代表相关游戏需求已被 QA 验收。`blocked` 只表示该次角色工作存在依赖，不意味着整个实验必须停止。

## 5. 可替换控制器

### 5.1 FixedLoopController

按预先固定的角色顺序循环执行：

```text
Designer → Art Producer → Developer → Player → QA
    ↑                                           │
    └───────────────────────────────────────────┘
```

- 后续轮次只处理当前待办，角色不必重复生成已有产物。
- 没有相关工作或不具备执行条件时，可按预先规定的确定性规则跳过。
- 跳过规则、可执行条件和待办表示对两组相同，不额外引入 LLM 调度判断。
- 不能把尚未生成报告误认为没有工作，例如首次启动时 Designer 应有初始化待办。
- 固定循环顺序可在开发集上选择，正式比较前冻结。

### 5.2 AdaptiveScheduler

读取当前状态、依赖、问题、证据和剩余预算，在可执行的角色中选择下一步工作。例如：

```text
Developer → Player → QA
                       ↓ 发现运行缺陷
                   Developer → Player → QA
                                            ↓ 发现视觉反馈问题
                                       Art → Developer → Player → QA
```

Scheduler 的决策输出至少包含下一角色、目标事项、目标和完成条件，并记录选择原因。它不直接写游戏、改需求或生成验收证据。

第一版固定每次调用的资源上限，主要比较调用对象与顺序。动态预算分配、模型选择、并行执行和角色增删留作单独的后续实验。

### 5.3 共同的停止与交付规则

- 两组使用相同的预算上限、超时处理和内部交付条件。
- 提前交付应满足预先定义的就绪条件，并有针对最终版本的启动与轨迹验证证据；仅凭 Scheduler 的判断不能绕过这些条件。
- 就绪条件来自公开 instruction 和交付协议，不包含隐藏评分结果。
- 预算耗尽或无法继续时，保留已生成产物、未解决事项与终止原因，并按相同规则提交已有结果。
- 最终版本选择规则在实验前固定；如允许保留并回退到已验证版本，两组都具有同样能力。
- 预留的最终验证与打包资源也应纳入总预算，并在两组中一致设置。

## 6. 对比实验约束

| 控制项 | 要求 |
| --- | --- |
| 角色能力 | 角色集合、提示词、模型配置、工具权限和单次工作约束一致 |
| 初始条件 | 同一任务、初始工作区、素材库、引擎版本与可用工具 |
| 上下文 | 共享状态结构、记忆更新和上下文截取规则一致 |
| 语言 | 所有模型提示词、请求上下文和角色输出使用英文；保留 Benchmark 原始英文 instruction，不翻译或改写；角色开发示例直接使用快照内的真实任务 |
| 资源预算 | 统一预算定义；Scheduler 的推理与调用消耗计入总消耗 |
| 执行方式 | 第一版都串行，避免把并行能力与调度策略混在一起 |
| 可见信息 | 不向生成角色或 Scheduler 暴露隐藏 rubric、参考解答和正式评分反馈 |
| 结束规则 | 预算耗尽、提前完成、失败记录和版本选择规则一致 |
| 评测配置 | Benchmark 版本、评测器与 judge 配置固定，并保存运行元数据 |

总预算应明确包含哪些资源，例如输入、输出及缓存 token、图像生成调用、引擎运行时间等。不同资源不宜默认视为等价；应记录明细，并预先说明采用的预算或成本口径。

主要报告官方总分及其各维度分数；同时记录启动成功率、轨迹重放成功率、成本、耗时和角色调用分布。自定义过程指标应与官方指标明确区分。失败任务不能从统计中静默排除。

在同一批任务上进行成对比较和重复运行，报告结果波动。调度规则与提示词在开发任务上调整，正式测试前冻结。Scheduler 是否更好是待验证的实验结论，不作为设计前提。

## 8. 建议开发顺序

1. 定义共享状态、产物引用、角色输入输出和运行日志结构。
2. 实现公共执行器、工具权限与预算约束，隔离生成环境与隐藏评测资料。
3. 实现五个角色，并优先打通游戏启动、真实操作、轨迹重放和证据回收。
4. 实现固定 Loop，使用单个开发任务跑通从 instruction 到完整交付的流程。
5. 在相同角色与状态之上实现 Scheduler。
6. 检查证据过期处理、预算终止、最终版本选择及两组能力是否一致。
7. 使用覆盖不同游戏类型的开发任务调试，再冻结配置开展正式对比。

第一版不额外拆出架构师、调试者、关卡设计者或发布经理。相关职责由已有角色承担，确定性的打包和文件检查由公共执行层完成。
